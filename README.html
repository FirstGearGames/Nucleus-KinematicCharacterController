Kinematic Character Controller for Nucleus

Kinematic Character Controller 3.4.4 characters, predicted by the player who controls them and checked by the server every tick, with KCC's motor itself left untouched.

The player's client moves its character the moment a key is pressed. The server runs the same KCC simulation from the same input, and when the two disagree the client is put back on the server's state and replays its newer ticks. Moving platforms, the boat and the planet are predicted with the character, so riding them needs no correction. Everyone else's character is drawn from the server's state.

Install

  1. Import Kinematic Character Controller 3.4.4 from the Asset Store.
  2. Import Nucleus for Unity, then this package.

Try it

  1. In Unity 6000.6.4f1, open Assets/Nucleus/Integrations/Kinematic Character Controller/Example/Scenes/NetworkCharacterPlayground.unity.
  2. Press Play, then Start Host. You are the host's player at KCC's usual starting spot.
  3. For a second player, open a ParrelSync clone (ParrelSync > Clones Manager), open the same scene there, press Play and Start Client. It connects to 127.0.0.1 on port 7777.

The playground is KCC's own CharacterPlayground, converted: eleven moving platforms, the boat on its timeline, the planet with its own gravity, six teleporters, two walking AI characters, seven loose cubes and the two launchers. KCC's original scene is still there and still plays offline.

How it works

KCC normally steps every motor and mover itself in FixedUpdate, and smooths them in LateUpdate. Under Nucleus a scene's NetworkKinematicCharacterSystem turns both off and steps KCC on the network tick instead:

  1. On each tick's early fixed update, every system this peer simulates enrolls its motor or mover. The server simulates every character; a client simulates the character it controls and the movers it predicts.
  2. Once every early fixed update has run, one KinematicCharacterSystem.Simulate steps the enrolled set in KCC's own order: mover velocities, every motor's first phase, mover moves, every motor's second phase. That order is what carries a character on a platform by the platform's move of the same tick.
  3. On the late fixed update, ValidatedKinematicCharacterMotor records the motor's whole state, KCC's own KinematicCharacterMotorState plus the capsule size, as validated members. The client sends a hash of them with its input; the server compares its own.
  4. On a mismatch Nucleus restores the client to the server's state for that tick and replays every tick since. Replayed ticks step KCC from the same hook, so the replay is the same simulation, not a separate code path.

Characters and movers are drawn through a GraphicalSmoother, which slides the drawn pose across each tick, so a 30 tick per second simulation looks smooth and a correction never snaps. The character's root, its colliders and KCC's own math always stay at the true pose.

Put it on your own character

  1. Add one NetworkKinematicCharacterSystem to the networked scene, beside the UnityCoreManager.
  2. On the character prefab, beside its KinematicCharacterMotor and your ICharacterController: add NetworkSystemObject, ValidatedKinematicCharacterMotor and a GraphicalSmoother whose Child Graphic is the object holding the meshes and the camera target.
  3. Write one NucleusBehaviour for your controller, as NetworkExampleCharacter does for NetworkExampleCharacterController:
    • input as MemberRole.Predict members, written on the controlling player's live tick, with presses declared isCarriedForward: false;
    • your controller's own state (timers, flags, modes) as MemberRole.Validate members, recorded on OnLateFixedUpdate and put back in OnReplayStarting;
    • the input handed to the controller on OnEarlyFixedUpdate of every simulated tick, replayed ones included.
  4. On every moving platform: NetworkSystemObject, ValidatedPhysicsMover, a GraphicalSmoother with Child Graphic off, and an IMoverController that reads ValidatedPhysicsMover.SimulationTime or the mover's own state instead of Time.time. NetworkMovingPlatform and NetworkPlayableMover are KCC's two examples done that way.
  5. Give each assembly definition that declares network types its own [assembly: NetworkBundle(n)]. This integration compiles into Assembly-CSharp, which is the main bundle and needs none.
  6. Run Tools > Nucleus, Build tab, Rebuild Network Prefab Collection, and save the scene so its scene objects are stamped.

What changed in KCC

Nothing. KCC runs exactly as the Asset Store ships it, and this package adds nothing to its folder. KCC has no assembly definitions, so it compiles into Assembly-CSharp, and this integration has none either, so that it can reference KCC from the same assembly. That holds wherever KCC is imported, Assets/Plugins included.

The networked characters run on NetworkExampleCharacterController rather than KCC's ExampleCharacterController. It moves the same way, but KCC's controller keeps its jump and crouch state in private fields, and a replay has to put that state back.

Things that look like bugs but are not

  • A character spawned on a moving platform or the planet is corrected once or twice in its first second. A client predicts movers ahead of the server, as it predicts its own character, so the deck it lands on is a little further along than where the server placed the character. It settles within a few ticks and rides with no corrections after that.
  • Other players feel slightly behind when you bump into them. Only your own character and the movers are predicted; other players are where the server last said, a round trip behind you. Pushing into one can cost a correction.
  • The loose cubes do not move when you walk into them. KCC's example character is authored with Rigidbody Interaction Type None, so it treats them as walls, offline too. The cubes are the server's: knocked by a launched cube, every player sees the server's result.
  • A teleporter fires a tick after you step into it. KCC's teleporters react to trigger callbacks, which a replay cannot repeat. Here the character tests its own capsule against each teleporter at the start of every tick, so stepping in at the end of one tick teleports at the start of the next, on the server and in every replay alike.
  • The camera turns in small steps on a fast spinning platform. KCC turns the camera by the rotation its own interpolation gives the platform, which is off. The camera turns by the platform's drawn rotation from frame to frame instead.

Troubleshooting

  • Characters stand still and nothing logs. The scene has no NetworkKinematicCharacterSystem. Each character and mover logs found no [NetworkKinematicCharacterSystem] in the scene when it wakes.
  • Every tick on a platform is a correction. The platform moves by Time.time or keeps state of its own that a replay does not rewind. Move it from SimulationTime or from the mover's own pose, as NetworkPlanet does.
  • A character on a platform is corrected every tick only after a restore. The platform has no ValidatedPhysicsMover. A motor's attached rigidbody travels as the mover's system Id, and a rigidbody that is not a networked mover is restored as none.
  • The console says two assemblies register network types under the same bundle Id. An assembly with network types has no [assembly: NetworkBundle(n)] of its own.

Tests

Tests/KinematicCharacterLivePlayTests.cs plays the playground between two editors over UDP. Each scenario is a pair: run Server_<Scenario> in the main editor's Test Runner (Play Mode) and Client_<Scenario> in a ParrelSync clone. The two meet through files in %TEMP%/kcc-live-tests, or the folder in KCC_TEST_DIRECTORY, on port 47781 unless KCC_TEST_PORT names another. Either side run alone times out. The tests compile into Assembly-CSharp with the integration, so this project turns on Enable playmode tests for all assemblies in Project Settings, Player.

Tests/NetworkExampleCharacterControllerReplayTests.cs runs in one editor with no network. It steps KCC by hand through a walk and a jump, puts the controller and motor back to the tick before the jump, replays the same input, and requires the replay to end within 0.0001 m of the original. That is the property a reconcile relies on, at a moment too fine to time between two processes.
